# 当前未完成事项与逐项讨论清单

用途：作为后续持久目标的讨论底稿；按优先级逐项确认范围、决策和验收条件。此文档不代表已经创建持久目标，也不代替生产操作授权。

## 当前基线

- P3 正式发布范围已完成：13 个语言首页生产回读、SEO、询盘写入、部署冷启动、smoke 23/23、SEO 合同 5/5 均有记录。

- 10 条 FLBOOK 产品当前为 `approved` / `claimsVerified=true`，有 76 条来源规格；复合肥料缺可靠定量表。
- 21 条新增官方候选仍为 `owner-review` / `claimsVerified=false`；原始 28 条候选中 7 条与 FLBOOK 按来源 ID 对应，候选审核包仍记录 3 组同名冲突。
- 13 种语言的路由已公开；CMS 缺译字段以英语源回退，不能视为人工译文完成。
- 工作区有大量尚未提交变更；生产运行版本与 Git 提交之间的发布追溯仍需整理。
- 生产本次依赖安装报告 19 条漏洞，其中 2 条 critical；尚未完成针对实际生产依赖路径的影响分析。

## P0：生产治理与安全

### 1. 固定发布基线与修正文档状态

**现状：** 当前分支为 `codex/haifa-reference-rebuild`，工作区包含大量未提交和未跟踪变更；生产已部署其中的代码。任务清单仍将 P2 参数确认、P3 发布决策列为未完成，阶段门禁也残留“英语回退待部署”的过期描述。

**需要讨论：**
- 这批工作应整理成一个发布提交，还是按功能拆成多个提交？
- 是否需要建立与生产当前版本对应的 tag/release 记录？
- 哪些历史验收文档保留为历史，哪些作为唯一当前状态来源？

**完成标准：**
- 生产运行代码可以追溯到明确的 Git commit/tag 和部署记录。
- `tasks/todo.md`、HANDOFF、阶段门禁、P3 决策和上线矩阵不再互相矛盾。
- 所有未提交修改有明确归属；没有未经说明的密钥、备份或临时文件进入版本控制。

**依赖：** 先盘点现有 diff 和未跟踪文件，不覆盖或丢弃用户已有改动。

### 2. 核查依赖漏洞

**现状：** 生产服务器 `npm ci` 报告 19 条漏洞，其中 2 条 critical；本次未运行自动升级。

**需要讨论：**
- 是否先做只读漏洞影响分析，再按生产可达性排序？建议先这样做。
- 对需要升级的依赖，采用最小版本修复还是安排框架/依赖批次升级？
- 是否需要在部署流水线设置高危漏洞门禁？

**完成标准：**
- 每条 high/critical 漏洞有对应包、生产可达性、修复版本和兼容性判断。
- 经批准的升级通过类型检查、重点回归和生产构建；未修复项有理由、负责人和复查时间。

**依赖：** 不在分析前执行 `npm audit fix --force` 或改变主要框架版本。

### 3. 收口生产验收产生的测试询盘

**现状：** 公网 smoke 与 SEO 合同会向启用状态的生产 API 写入验收询盘。当前没有证据说明本轮所有测试记录已在后台关闭或隔离。

**需要讨论：**
- 是否由管理员将可识别的验收记录设为 `closed`？
- 后续生产验收是否使用显式 `test` 标识、专用邮箱和固定来源路径？
- 是否允许未来测试记录自动归档；保留期限如何定？

**完成标准：**
- 只读盘点确认测试记录，不误操作真实客户询盘。
- 已确认的验收记录按决定关闭/标记，真实记录保持原状。
- 测试有稳定可识别标识，生产统计能够排除验收数据。

**依赖：** 查看生产记录前使用只读查询；批量删除不在默认处理范围内。

## P1：询盘业务闭环

### 4. 决定询盘通知与处理方式

**现状：** Contact 表单可提交并写入 Payload `inquiries`；管理员可查看和更新状态；当前没有 SMTP/API 通知适配器。邮箱与 WhatsApp 是页面上的直接联系渠道，不等价于询盘自动转发。

**需要讨论：**
- 方案 A：继续后台人工处理，明确谁值守、多久检查一次、响应 SLA 和积压升级方式。
- 方案 B：增加邮件通知；确认收件人、SMTP/API 服务、测试收件箱、失败重试和送达日志。
- 方案 C：接入工单/CRM；确认目标系统、字段映射、幂等键和失败补偿。
- 询盘是否需要国家、电话、客户角色等字段设为必填？

**完成标准：**
- 每条询盘有明确接收责任人及处理 SLA。
- 若启用通知，端到端测试证明可投递、失败可见、重试不会重复创建。
- 前端成功提示和隐私说明准确描述数据去向；不以 HTTP 201 代替通知送达证据。

**依赖：** 用户选择 A/B/C 后再定接口和部署改动；SMTP/API 凭据不得写进仓库或聊天。

### 5. 明确询盘隐私与反垃圾运行规则

**现状：** 已有同意勾选、蜜罐和访问权限边界；需要把用户可见隐私说明和运营留存规则与真实处理流程对齐。

**需要讨论：**
- 隐私告知由现有文案补充，还是提供独立隐私页面？
- 询盘保留多久，谁可访问，客户要求删除时如何处理？
- 当前蜜罐是否足够；达到什么垃圾量后启用速率限制、验证码或边缘防护？

**完成标准：**
- 表单明确告知收集字段、用途、访问方、保留/删除方式。
- 处理流程与 Payload 权限、实际通知渠道一致。
- 反垃圾措施在正常客户可提交的同时，有可观测的拒绝/限流证据。

**依赖：** 通知方式和业务负责人确定后定稿隐私文案。

## P1：正式产品目录决策

### 6. 决定 21 条官方候选的展示和审核状态

**现状：** 28 条来源候选中，7 条依据来源 ID 与 FLBOOK 产品对应，21 条以独立候选展示；这 21 条仍是 `owner-review` / `claimsVerified=false`。审核包指出 3 组同名冲突，不能单凭名称合并。

**需要讨论：**
- 三组同名记录分别是同一产品的不同型号、不同包装，还是不同产品？需要按源产品 ID/型号逐组确认。
- 在确认前，候选卡片是否继续公开展示？若继续，是否显示“资料待核实”提示？
- 对不上型号或资料不足的候选，是隐藏、保留预览，还是只展示目录名和来源链接？
- 哪些候选进入正式目录，哪些继续待审，哪些排除？

**完成标准：**
- 28 条候选逐条有保留/合并/发布/隐藏决定，三组冲突有独立决定。
- 合并使用稳定来源 ID 和型号，不按近似名称自动合并。
- 未批准记录不被标记为 claims verified；公开状态与审核决定一致。

**依赖：** 业主提供或确认型号、包装和当前销售状态；决策依据见 `official-site-candidate-review-packet-2026-11-09.md`。

### 7. 补充正式产品资料的明确缺项

**现状：** 10 条 FLBOOK 产品已按业主授权批准；76 条规格来自画册。复合肥料缺可靠定量表，不能以猜测补齐。候选产品的技术资料仍待审核。

**需要讨论：**
- 复合肥料是否有新的正式技术表或包装标签可作为定量来源？没有的话，是否明确保持无定量表？
- 21 条候选中哪些有当前型号、包装、施用说明、认证/证书、销售状态的正式资料？
- “10 条按 FLBOOK + 原官网资料批准”的授权是否只覆盖现有资料，不覆盖新增的冲突型号？建议将这条边界写入审核记录。

**完成标准：**
- 有来源的字段记录来源和单位；缺失字段清楚显示联系入口或未提供。
- 证书、效果、施用量、销售状态没有无来源推断。
- 产品列表、详情、筛选和后台字段与最终决定一致。

**依赖：** 候选产品决定；若业主确认缺资料，则以“保持缺失并明确展示”为完成，不继续无限追索证据。

## P2：多语言内容与发布质量

### 8. 制定 13 种语言的机器翻译与人工审校流程

**现状：** 13 种语言路由已公开；通用 UI 字典覆盖 13 个 locale，CMS 缺译使用英语源回退。路由和页面可用，不代表业务内容已译完。

**需要讨论：**
- 按此前授权，是否由机器翻译生成缺失译文并进入后台审核，而不是直接作为已批准内容发布？
- 优先覆盖哪些页面和语言？建议先产品详情、Contact/FAQ、SDS/质量信息，再新闻、知识和案例。
- 审校采用业主逐条确认、术语审校人抽检，还是先全部标成 machine-translated 并按风险复核？
- 哪些法律、安全、产品参数内容禁止仅靠机器翻译直接上线？

**完成标准：**
- 每个本地化字段可以区分人工批准、机器草稿、英语回退和缺失。
- 高风险数值、单位、认证、施用说明有双语对账记录。
- 13 种语言的关键页面经本地化/RTL 检查；英语回退不会被误报为译文完成。

**依赖：** 确认机器翻译进入审核流程的规则、优先语言和人工审核责任人。

## P2：视觉素材与浏览器矩阵

### 9. 完成图片语义匹配和全语言关键页浏览器复验

**现状：** 媒体审计确认 14 个中英页面、21 个唯一媒体无重复哈希和 generated/prototype 引用；390px Hebrew RTL 首页无溢出、无已加载失败图片。哈希唯一不能证明图片主题与所在页面文案完全匹配。

**需要讨论：**
- 是否按首页、产品、公司、技术文章、案例五类制作图片—文案对照表，由业主确认不匹配项？
- 视觉验收最小覆盖是 13 语言首页，还是 13 语言的首页、产品列表、产品详情、Contact、FAQ？
- 桌面/移动断点采用 1280px 与 390px，是否另加超窄屏和 RTL 长文本？

**完成标准：**
- 页面主图与产品/主题匹配，不出现不同产品错误复用或明显文图错位。
- 约定的语言×页面×视口矩阵有截图和结果；失败项修复后复验。
- 只报告实际覆盖矩阵，不把样本页结果泛化为全站验收。

**依赖：** 翻译优先级确定后选择代表页面和长文本样本。

## P2：运维连续性

### 10. 建立定期备份、监控和恢复演练

**现状：** 有 PostgreSQL 与媒体备份/恢复脚本；本次部署前做了数据库、媒体和上一版 standalone 备份，过去有隔离恢复证据。尚未确认自动排程、异地复制、失败告警和定期演练是否已运行。

**需要讨论：**
- 备份频率、保留周期、异地位置和加密要求是什么？
- readiness、磁盘、服务崩溃、备份失败和询盘积压需要哪些告警？由谁收到？
- 恢复演练频率和可接受 RPO/RTO 是多少？
- systemd 停止超时如何调整，以降低本次重启窗口出现短暂 502 的概率？

**完成标准：**
- 自动备份覆盖数据库和媒体，报告成功/失败且可发现。
- 至少按约定周期进行隔离恢复演练，验证数据库和媒体关联一致。
- 服务与磁盘故障告警经过一次可控验证；RPO/RTO 有负责人接受。

**依赖：** 先确认托管位置、保留成本、通知渠道与责任人，再选具体实现。

## 建议讨论顺序

1. 先确认第 1 项发布基线和文档状态，避免目标建立在错误快照上。
2. 讨论第 2 项安全漏洞核查与第 3 项测试询盘清理，控制当前生产风险和数据噪声。
3. 讨论第 4、5 项询盘运营与隐私，决定是否仅后台处理或建设通知闭环。
4. 按第 6、7 项逐条处理候选产品冲突和正式资料缺项。
5. 确认第 8 项翻译流程，再安排第 9 项视觉和浏览器矩阵。
6. 最后将第 10 项备份、监控和恢复演练常态化；其中备份基线可与前面并行启动。

每次讨论只收敛一个事项：确认范围、负责人、决策项和验收条件后，再创建对应持久目标。需要架构选择的事项保留多个选项，不在清单阶段预设结论。
