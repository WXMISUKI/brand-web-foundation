## P0：生产治理与安全

### 1. 固定发布基线与修正文档状态

**现状：** 当前分支为 `codex/haifa-reference-rebuild`。生产服务 active、readiness 通过；最新只读产品审计与当前阶段闸门一致。P2/P3 历史验收文件和部分任务条目仍保留更早状态，发布 commit 也无法从服务器 Git 元数据核实。

**需要讨论：**
- 这批工作应整理成一个发布提交，还是按功能拆成多个提交？
- 是否需要建立与生产当前版本对应的 tag/release 记录？
- 哪些历史验收文档保留为历史，哪些作为唯一当前状态来源？

**完成标准：**
- 当前与历史状态清晰分开；最新产品、语言、询盘和 SEO 状态有唯一当前入口。
- 生产后续发布保留实际 Git commit、build ID、依赖版本和回滚点。
- 所有未提交修改有明确归属；没有未经说明的密钥、备份或临时文件进入版本控制。

**依赖：** 先盘点现有 diff 和未跟踪文件，不覆盖或丢弃用户已有改动。

### 2. 核查依赖漏洞

**现状：** 生产锁文件使用 Next 16.3.5、Payload 3.92.0、Sharp 0.34.5；官方 registry audit 为 19 项（7 low、6 moderate、4 high、2 critical），包括 Next/DOMPurify critical 及 Sharp/happy-dom high。当前工作区已准备 Next 16.4.5、Payload 3.93.0、Sharp 0.35.5 与 DOMPurify/happy-dom 定向覆盖；其锁文件 audit 为 13 项（7 low、6 moderate，0 high/critical），但尚未部署。

**需要讨论：**
- 检查 direct/override 路径、框架兼容性、锁文件一致性及部署构建结果。
- 确认生产部署窗口、备份与回滚点后，再部署已准备的依赖升级。
- 评估 CI 高危漏洞门禁是否需要单独建立，避免把低/中危或不可兼容的自动降级当作发布阻断。

**完成标准：**
- 每条 high/critical 漏洞有对应包、生产可达性、修复版本和兼容性判断。
- 经批准的升级通过类型检查、重点回归和生产构建；未修复项有理由、负责人和复查时间。

**依赖：** 不执行 `npm audit fix --force`；生产升级仍需单独部署授权和发布验收。

### 3. 收口生产验收产生的测试询盘

**现状：** 公网 smoke 与 SEO 合同会向启用状态的生产 API 写入验收询盘。当前没有证据说明本轮所有测试记录已在后台关闭或隔离。

**需要讨论：**
- 是否由管理员将可识别的验收记录设为 `closed`？
- 后续生产验收是否使用显式 `test` 标识、专用邮箱和固定来源路径？
- 是否允许未来测试记录自动归档；保留期限如何定？

**完成标准：**
- 只读盘点确认测试记录，不误操作真实客户询盘。
- 已确认的验收记录按决定关闭/标记，真实记录保持原状。
- 测试有稳定可识别标识，生产统计能够排除验收数据。

**依赖：** 查看生产记录前使用只读查询；批量删除不在默认处理范围内。

## P1：询盘业务闭环

### 4. 决定询盘通知与处理方式

**现状：** Contact 表单可提交并写入 Payload `inquiries`；管理员可查看和更新状态；当前没有 SMTP/API 通知适配器。邮箱与 WhatsApp 是页面上的直接联系渠道，不等价于询盘自动转发。

**业主已选：** 先由 Payload 后台人工处理，不接邮件或 CRM 通知；所有后台账号可查看和处理。目前仅有 `leon@kowloonglobaltrading.com` 一个账号，由后台常驻人员留意新询盘；无需固定检查频率或首次响应 SLA，也不对外承诺响应时限。

**需要讨论：**
- 方案 A（已选）：继续后台人工处理；使用当前 Payload 账号体系，由常驻后台人员留意。无需固定检查频率或响应 SLA，页面不承诺响应时限。
- 方案 B：增加邮件通知；确认收件人、SMTP/API 服务、测试收件箱、失败重试和送达日志。
- 方案 C：接入工单/CRM；确认目标系统、字段映射、幂等键和失败补偿。
- 询盘是否需要国家、电话、客户角色等字段设为必填？

**完成标准：**
- 每条询盘有明确接收责任人及处理 SLA。
- 若启用通知，端到端测试证明可投递、失败可见、重试不会重复创建。
- 前端成功提示和隐私说明准确描述数据去向；不以 HTTP 201 代替通知送达证据。

**依赖：** 用户选择 A/B/C 后再定接口和部署改动；SMTP/API 凭据不得写进仓库或聊天。

### 5. 明确询盘隐私与反垃圾运行规则

**现状：** 已有同意勾选、蜜罐和访问权限边界；需要把用户可见隐私说明和运营留存规则与真实处理流程对齐。

**需要讨论：**
- 隐私告知由现有文案补充，还是提供独立隐私页面？
- 询盘保留多久，谁可访问，客户要求删除时如何处理？
- 当前蜜罐是否足够；达到什么垃圾量后启用速率限制、验证码或边缘防护？

**完成标准：**
- 表单明确告知收集字段、用途、访问方、保留/删除方式。
- 处理流程与 Payload 权限、实际通知渠道一致。
- 反垃圾措施在正常客户可提交的同时，有可观测的拒绝/限流证据。

**依赖：** 通知方式和业务负责人确定后定稿隐私文案。

### 6. 决定 21 条官方候选的展示和审核状态

**现状：** 28 条来源候选中，7 条依据来源 ID 与 FLBOOK 产品对应，21 条以独立候选记录保留；这 21 条仍是 `owner-review` / `claimsVerified=false`。审核包指出 3 组同名来源记录；展示可以按同名分组，但不能因此合并 CMS 记录或放宽审核状态。

**展示决策：** 业主确认候选名称和图片继续公开，并通过 Contact 接受询盘。工作区将两个候选内部重名组分别合为一个目录卡，详情保留来源图片；已获批 FLBOOK 产品不因源站重名被覆盖，所有候选审核字段保持原状。部署前 production 仍保持旧目录展示。

**需要讨论：**
- 三组同名记录分别是同一产品的不同型号、不同包装，还是不同产品？需要按源产品 ID/型号逐组确认。
- 在确认前，候选卡片是否继续公开展示？若继续，是否显示“资料待核实”提示？
- 对不上型号或资料不足的候选，是隐藏、保留预览，还是只展示目录名和来源链接？
- 哪些候选进入正式目录，哪些继续待审，哪些排除？

**完成标准：**

- 合并使用稳定来源 ID 和型号，不按近似名称自动合并。
- 未批准记录不被标记为 claims verified；公开状态与审核决定一致。

**依赖：** 业主提供或确认型号、包装和当前销售状态；决策依据见 `official-site-candidate-review-packet-2026-11-09.md`。

**需要讨论：**

**完成标准：**

**依赖：** 候选产品决定；若业主确认缺资料，则以“保持缺失并明确展示”为完成，不继续无限追索证据。

## P2：多语言内容与发布质量

### 8. 制定 13 种语言的机器翻译与人工审校流程

**现状：** 13 种语言路由已公开；通用 UI 字典覆盖 13 个 locale，CMS 缺译使用英语源回退。业主确认默认英语，全部 13 种语言的界面文案和当前可见业务内容均需翻译，由 Codex 起草并自审；缺少来源的字段不补写内容，翻译也不改变原审核状态。

**需要讨论：**
- 根据实际访问和询盘来源确定 12 种非英语语言的实施批次；完成一批后做关键页面、术语和 RTL 复核。
- 法律、安全、产品参数和候选审核态只翻译现有来源文本；不创作新 claims、施用建议、证书或法律承诺。
- 翻译完成不改变审核状态；高风险产品/法规译文需业主或专业审校人确认后才可标为已审校。

**完成标准：**
- 13 种公开语言的界面文案和当前可见业务内容有逐语言覆盖清单；英语回退不会被误报为翻译完成。
- 高风险数值、单位、认证和施用说明有来源与术语对账记录，原审核状态保持不变。
- 关键页面经本地化和 RTL 检查；记录实际完成的语言×页面范围。

**依赖：** 确认目标市场优先级；之后按批次实现和复核。

## P2：运维连续性

### 10. 建立定期备份、监控和恢复演练

**现状：** 有 PostgreSQL 与媒体备份/恢复脚本；本次部署前做了数据库、媒体和上一版 standalone 备份，过去有隔离恢复证据。尚未确认自动排程、异地复制、失败告警和定期演练是否已运行。

**需要讨论：**
- 备份频率、保留周期、异地位置和加密要求是什么？
- readiness、磁盘、服务崩溃、备份失败和询盘积压需要哪些告警？由谁收到？
- 恢复演练频率和可接受 RPO/RTO 是多少？
- systemd 停止超时如何调整，以降低本次重启窗口出现短暂 502 的概率？

**完成标准：**
- 自动备份覆盖数据库和媒体，报告成功/失败且可发现。
- 至少按约定周期进行隔离恢复演练，验证数据库和媒体关联一致。
- 服务与磁盘故障告警经过一次可控验证；RPO/RTO 有负责人接受。

**依赖：** 先确认托管位置、保留成本、通知渠道与责任人，再选具体实现。

## 建议讨论顺序

1. 先确认第 1 项发布基线和文档状态，避免目标建立在错误快照上。
2. 讨论第 2 项安全漏洞核查与第 3 项测试询盘清理，控制当前生产风险和数据噪声。
3. 讨论第 4、5 项询盘运营与隐私，决定是否仅后台处理或建设通知闭环。
4. 按第 6、7 项逐条处理候选产品冲突和正式资料缺项。
5. 确认第 8 项翻译流程，再安排第 9 项视觉和浏览器矩阵。
6. 最后将第 10 项备份、监控和恢复演练常态化；其中备份基线可与前面并行启动。

每次讨论只收敛一个事项：确认范围、负责人、决策项和验收条件后，再创建对应持久目标。需要架构选择的事项保留多个选项，不在清单阶段预设结论。
